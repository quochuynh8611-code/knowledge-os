## 1. CONTEXT & PROBLEM STATEMENT

### 1.1. Background
Người dùng thường xuyên chuyển đổi giữa việc đọc/ghi chú (Notes) và tạo flashcard để ôn tập. Hiện tại, quy trình này đòi hỏi:
1. Copy text từ Note
2. Mở Flashcard Modal
3. Paste vào form
4. Chọn topic
5. Submit

Quy trình thủ công này gây gián đoạn flow nghiên cứu và giảm tần suất tạo thẻ.

### 1.2. Problem
Làm thế nào để tích hợp seamless việc tạo flashcard trực tiếp từ Note Reader, giảm friction và tăng conversion rate (note → flashcard)?

### 1.3. Scope
- US1: Tạo thẻ từ text bôi đen (selection → popover → modal)
- US2: Auto-detect Cloze Deletion syntax
- US3: Batch import từ bullet list
- US4: Hiển thị danh sách thẻ liên kết trong Note Reader

### 1.4. Constraints
- Không migration database mới (schema đã có `Flashcard.noteId`)
- Không dependency mới (no `DOMPurify`, no `marked`)
- Tận dụng components hiện có (`FlashcardFormModal`, `clozeParser`, `NoteReaderModal`)
- Test-first (TDD), không code production trước khi có failing tests

## 3. CONSIDERED OPTIONS

### 3.1. Text Selection Popover Architecture

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **A: Fixed + getBoundingClientRect()** | Position popover bằng `fixed` CSS + tọa độ từ `selection.getRangeAt(0).getBoundingClientRect()` | - Đơn giản, dễ implement<br>- Scroll-safe<br>- Không cần portal | - Có thể bị che bởi fixed headers (edge case)<br>- Cần tính toán z-index cẩn thận |
| **B: React Portals** | Mount popover ra ngoài DOM tree bằng `createPortal()` | - Không bị ảnh hưởng bởi overflow/positioning của parent<br>- Z-index dễ quản lý | - Phức tạp hơn<br>- Cần portal container<br>- Debug khó hơn |
| **C: Absolute within container** | Position bằng `absolute` relative với NoteReaderModal container | - Đơn giản nhất<br>- Không cần tính toán viewport | - Bị clipping nếu container có `overflow: hidden`<br>- Không scroll-safe |

**Decision**: ✅ **Option A** (Fixed + getBoundingClientRect())

**Rationale**: 
- Đủ tốt cho 95% use cases
- Đơn giản, dễ debug
- Scroll-safe (critical UX requirement)
- Nếu gặp edge case với fixed headers, sẽ adjust z-index hoặc offset sau

### 3.2. Cloze Detection Strategy

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **A: Simple Regex** | Pattern `/\{\{c(\d+)::(.+?)\}\}/g` với non-greedy match | - Đơn giản, nhanh<br>- Đủ cho 95% cases<br>- Dễ maintain | - Không handle nested braces (hiếm)<br>- Edge cases cần validation thêm |
| **B: Full Parser** | Custom parser với stack-based brace matching | - Handle nested braces<br>- Chính xác 100% | - Phức tạp, khó debug<br>- Overkill cho use case hiện tại |
| **C: Library (remark/remark-gfm)** | Dùng markdown parser có sẵn với extension | - Robust, đã test nhiều<br>- Support nhiều syntax | - Dependency mới<br>- Overhead bundle size<br>- Learning curve |

**Decision**: ✅ **Option A** (Simple Regex)

**Rationale**:
- Nested braces là edge case rất hiếm trong thực tế
- Regex đủ cho multi-cloze (`{{c1::A}}` và `{{c2::B}}`)
- Có thể enhance sau nếu cần (với validation layer)

### 3.3. Batch Import Design

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **A: Sequential Creation** | Gọi API tuần tự (1-by-1) với progress indicator | - Đơn giản, dễ debug<br>- Handle errors individually<br>- Progress rõ ràng | - Chậm hơn với large batches (>50 cards) |
| **B: Parallel Creation** | Gọi API song song với `Promise.all()` | - Nhanh hơn<br>- Tận dụng network concurrency | - Khó handle errors individually<br>- UX phức tạp (partial failures)<br>- Risk overload server |
| **C: Server-side Batch Endpoint** | Tạo endpoint mới `POST /api/flashcards/batch` | - Single API call<br>- Server optimize transaction | - Backend complexity<br>- Migration risk<br>- Violates "no new endpoints" constraint |

**Decision**: ✅ **Option A** (Sequential Creation)

**Rationale**:
- Max 50 cards/lần là đủ cho hầu hết use cases
- Sequential đủ nhanh (<2s cho 50 cards với local API)
- Dễ handle errors, rollback, và show progress
- Có thể optimize sang parallel sau nếu cần

### 3.4. Security & Sanitization

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **A: React Auto-escape** | Dựa vào React JSX auto-escape, không dùng `dangerouslySetInnerHTML` | - Built-in security<br>- Không dependency<br>- Đơn giản | - Không protect khỏi logic bugs (hiếm) |
| **B: DOMPurify** | Thêm library `DOMPurify` để sanitize HTML | - Robust, industry standard<br>- Protect khỏi XSS phức tạp | - Dependency mới<br>- Bundle size tăng<br>- Không cần thiết với current architecture |
| **C: Custom Sanitizer** | Tự implement whitelist-based sanitizer | - Control hoàn toàn<br>- Không dependency | - Risk bugs<br>- Maintenance burden<br>- Khó test hết edge cases |

**Decision**: ✅ **Option A** (React Auto-escape)

**Rationale**:
- Current architecture không inject raw HTML (no `dangerouslySetInnerHTML`)
- `MarkdownReadabilityRenderer` dùng lexer thuần TS, output React elements
- React auto-escape đủ protect khỏi XSS trong 99% cases
- Thêm `DOMPurify` chỉ cần thiết nếu render HTML từ external sources

### 3.5. Performance Optimization

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **A: Debounce + Memoization** | Debounce 100ms cho `selectionchange`, memoize position calculation | - Giảm re-renders<br>- Responsive<br>- Đơn giản | - slight latency (100ms) |
| **B: Throttle** | Throttle 200ms cho `selectionchange` | - Giảm re-renders mạnh hơn | - Lag cảm nhận được khi drag selection |
| **C: No Optimization** | Re-render mỗi `selectionchange` event | - Responsive nhất | - Performance tệ với large notes<br>- Battery drain |

**Decision**: ✅ **Option A** (Debounce + Memoization)

**Rationale**:
- 100ms debounce là imperceptible với user
- Balance tốt giữa performance và UX
- Memoization tránh recalculations không cần thiết

## 4. FINAL DECISION SUMMARY

| Aspect | Decision |
|--------|----------|
| **Popover Architecture** | Fixed + `getBoundingClientRect()` (Option A) |
| **Cloze Detection** | Simple Regex `/\{\{c(\d+)::(.+?)\}\}/g` (Option A) |
| **Batch Import** | Sequential API calls, max 50 cards (Option A) |
| **Security** | React auto-escape, no `dangerouslySetInnerHTML` (Option A) |
| **Performance** | Debounce 100ms + memoization (Option A) |

## 5. CONSEQUENCES

### 5.1. Positive
- **UX**: Giảm friction đáng kể (3-5 clicks → 1 click)
- **Security**: Không dependency mới, attack surface nhỏ
- **Performance**: Responsive với debounce, scroll-safe popover
- **Maintainability**: Code đơn giản, dễ debug, dễ extend
- **Testability**: TDD-friendly, dễ viết unit tests cho parser + popover logic

### 5.2. Negative
- **Edge Cases**: Popover có thể bị che bởi fixed headers (hiếm, sẽ fix sau nếu cần)
- **Nested Cloze**: Không handle nested braces (edge case rất hiếm)
- **Batch Speed**: Sequential chậm hơn parallel (acceptable với max 50 cards)

### 5.3. Risks & Mitigation
| Risk | Impact | Mitigation |
|------|--------|------------|
| **Popover positioning bugs** | Medium | Test trên multiple browsers, screen sizes; adjust offset nếu cần |
| **XSS từ user input** | High | React auto-escape + Zod validation + no raw HTML |
| **Performance với large notes** | Medium | Debounce 100ms, memoization, lazy load NoteCardListSection |
| **Batch creation timeout** | Low | Max 50 cards, sequential với timeout per call |
